# Application audio capture — issue #27

Included in **1.2.3**. The user confirmed application selection on the ARM64 test MSIX on
8 September 2026; whether the audio is really isolated, and what happens when devices change,
are still to be checked.

For System or Both sources, choose **System capture → One application**, select an open
application, and run the level-only audio test before starting a live provider session.
**Refresh applications** updates the list. The other mode, **All audio on the selected
output**, keeps the choice of the default or a specific output device. Rehearsal and the
built-in demonstration use their own fixed input and do not capture applications. Local Whisper receives the same selected process tree as a cloud
engine; see [local Whisper](local-whisper.md) for buffering and offline operation.

The list shows accessible processes with visible top-level windows, distinguished by window
title and PID. Multiple windows of one process share one entry. Background-only and
inaccessible processes are not listed. The list has no per-app icons and does not group
unrelated process trees.

Listing opens a `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE` handle on each of those
processes, to read its creation time and whether it is still running; such a handle can neither read
memory nor run code. The list is built only while **One application** is selected (when the
mode is chosen, and on **Refresh applications**), so capturing the whole output opens no handle on another
process. That is the mode to suggest to players: kernel anti-cheat watches the handles opened
on a game.

## Capture scope and lifecycle

- WASAPI includes only the selected process and its descendants. No exclusion mode is used.
- Notifications generated by that application are included. A browser process may include
  several tabs; a single tab's audio cannot be selected.
- The mode is remembered, but the selected process is never saved. Select the application
  again each time the app starts. Selecting a process does not start capture.
- The process creation timestamp is checked alongside its PID, and a live process handle
  is kept open, so PID reuse cannot silently redirect capture to another process.
- When the parent process exits, that source stops. A working microphone can continue. The
  recovery action stops and drains the session, keeps the transcript and asks for a new
  selection.
- A missing selection, unsupported Windows version or capture failure never falls back to
  all system audio. Only the operator can switch to that mode.
- Windows build 20348 is the minimum. Process loopback is independent of a render endpoint;
  it uses explicit 48 kHz stereo float format and a 20 ms shared/event buffer request.
  Unsupported process-client methods, such as device mix-format and period queries, are not called.
- The resampling, metering, bounded audio queues and provider clients the app already has
  are reused.
  Enumeration and process checks do not run in the realtime microphone callback.
- Only the operator capability can enumerate applications; the overlay cannot invoke it.

## Verification

Automated tests check mode preservation, missing/unsupported/stale selections,
process identity forwarding to preflight, selector behaviour and the command capability
boundary. Windows tests enumerate application windows and open a process-loopback client
against an owned silent child process, then check process exit and stale creation times.

Manual acceptance testing is still pending in development builds and packaged NSIS/MSIX builds. Run the
isolation and process-exit cases with Whisper as well as a cloud engine, and let Whisper's
backlog drain after Stop before judging the transcript.

| Scenario | Expected result |
| --- | --- |
| Teams/Zoom plus unrelated media | Only the selected application's process tree is captured |
| Browser with multiple tabs | Scope is explained; verify which tabs share the selected tree |
| Microphone + application | Both meters/captions work; an app failure leaves the mic available |
| App exit and restart | Capture stops; explicit reselection required; transcript retained |
| Default-output or Bluetooth/dock change | Application scope stays selected; verify capture continuity |
| Minimized app, multiple windows | Selection remains stable; no duplicate entry for one PID |
| No application audio | Silence, without a false disconnection |
| Unsupported Windows | Explanatory message; all-output capture only after explicit selection |
| Demo and rehearsal | Existing fixture behaviour remains unchanged |

The silent-process smoke test cannot establish real Teams/Zoom/browser isolation or hardware
transitions. Issue #27 was closed at the user’s request for release 1.2.3.
